# docx-service

Веб-система для заполнения протоколов сердечно-лёгочной реанимации (СЛР), ведения архива записей и асинхронного формирования документов DOCX и PDF.

## Назначение и возможности

Системой пользуется оператор веб-формы. Она принимает данные протокола, проверяет их формат, сохраняет исходные и подготовленные данные в PostgreSQL и позволяет получить сформированные документы из архива.

- Форма СЛР с режимами `basic` и `full`, хронометражными таблицами и клиентской проверкой ключевых полей.
- Черновик формы сохраняется в `localStorage` браузера и восстанавливается после перезагрузки.
- Серверная валидация JSON, времени, календарных дат, номеров `kv_num` и значений таблиц; ошибки отображаются в форме.
- Архив с поиском по `kv_num`, фильтрами по дате сохранения и наличию DOCX/PDF, пагинацией и карточкой записи.
- Сохранение записи без рендера и постановка версии документа в очередь. Номер `kv_num` уникален среди непустых значений.
- Асинхронное формирование DOCX по `template.docx`, затем PDF через Gotenberg; статусы и ошибки рендеров видны в архиве.
- Скачивание выбранной версии DOCX и актуального PDF.

## Архитектура

```text
Пользователь
    |
    v
nginx (HTTP → HTTPS, TLS)
    |
    v
Express / веб-интерфейс ────────── PostgreSQL
    |                                  |
    |                                  v
    +── очередь archive_renders ── DOCX-воркер ── каталог DOCX
                                      |
                                      v
                              PDF-воркер ── Gotenberg ── каталог PDF
```

В Compose запускаются сервисы `db`, `app`, `worker`, `gotenberg`, `pdf-worker` и `nginx`. Приложение слушает порт 3000 только внутри Docker-сети; на хост публикуются nginx-порты 80 и 443. Воркеры получают задания опросом таблицы `archive_renders`; отдельного брокера очереди нет.

## Технологии

- Node.js 20 (образ `node:20-alpine`), JavaScript и Express 4.
- PostgreSQL 16 (`postgres:16-alpine`) и драйвер `pg`.
- DOCX: `docxtemplater` и `pizzip`; PDF: Gotenberg 8.
- Клиентские ES-модули, HTML/CSS; Babel собирает совместимую копию скриптов формы в `public/js-legacy`.
- Docker Compose и nginx 1.27-alpine.

## Структура проекта

```text
├── index.js                 # Express, статика и подключение маршрутов
├── routes/                  # UI, API архива и постановка рендера
├── lib/                     # валидация, нормализация, БД и рендер DOCX
├── worker/                  # отдельные DOCX- и PDF-воркеры
├── migrations/              # SQL-схема и последующие изменения БД
├── public/                  # форма, архив, стили и исходные скрипты
├── nginx/default.conf       # TLS и reverse proxy
├── template.docx            # рабочий шаблон DOCX
├── Dockerfile
├── docker-compose.yaml
├── backup_db.sh             # резервное копирование PostgreSQL
└── restore_db.sh            # восстановление PostgreSQL (разрушительная операция)
```

`template_old.docx` и `template_old2.docx` находятся в репозитории, но код рендера использует только `template.docx`.

## Требования

- Docker Engine с Docker Compose для штатного развёртывания.
- Свободные порты хоста 80 и 443.
- Права на запись в каталоги документов, монтируемые в контейнеры как `/mnt/docx` и `/mnt/pdf`.
- TLS-сертификат и закрытый ключ в `nginx/certs/`.
- При запуске без Docker: Node.js 20, PostgreSQL и доступный экземпляр Gotenberg для PDF.

## Переменные окружения

В коде нет `.env.example`. В `docker-compose.yaml` часть значений задана прямо в разделе `environment`; для производственной установки учётные данные БД следует заменить в Compose и не хранить в Git. Секреты ниже приведены только как заполнители.

| --- | --- | --- | --- |

| `PORT` | нет | Порт Express, по умолчанию `3000` | `3000` |

## Установка и первый запуск

1. Получите исходный код и перейдите в каталог проекта.

   ```bash
   git clone <URL_РЕПОЗИТОРИЯ>
   cd docx-service
   ```

2. Проверьте и измените перед запуском `docker-compose.yaml`: учётные данные PostgreSQL, строку `DATABASE_URL`, а также хостовые каталоги хранения. В текущем файле используются bind mount'ы `/srv/slr-docx:/mnt/docx` и `/srv/slr-pdf:/mnt/pdf`; создайте их и предоставьте Docker право записи.

   ```bash
   mkdir -p /srv/slr-docx /srv/slr-pdf
   ```

3. Поместите сертификат и ключ в `nginx/certs/`. Имена файлов и имя хоста задаются в `nginx/default.conf`; сертификат должен им соответствовать. Каталог сертификатов игнорируется Git.

4. Соберите и запустите стек.

   ```bash
   docker compose up -d --build
   ```

   На первом запуске PostgreSQL выполнит все SQL-файлы из `migrations/`, поскольку они смонтированы в `/docker-entrypoint-initdb.d`.

5. Проверьте состояние и откройте адрес HTTPS, соответствующий `server_name` в `nginx/default.conf`, затем страницу `/form`.

   ```bash
   docker compose ps
   ```

## Управление контейнерами

```bash
# Запуск существующих образов
docker compose up -d

# Пересборка и запуск после изменения кода или образов
docker compose up -d --build

# Остановка без удаления контейнеров
docker compose stop

# Повторный запуск сервисов
docker compose restart

# Остановка и удаление контейнеров/сети, но без именованного тома БД
docker compose down

# Журналы всех сервисов
docker compose logs -f

# Журнал конкретного сервиса
docker compose logs -f pdf-worker
```

`docker compose stop` сохраняет контейнеры. `docker compose down` удаляет контейнеры и сеть, но не именованный том `db_data`. Не используйте `docker compose down -v` для обычного перезапуска: эта команда удаляет том базы данных.

## Проверка работоспособности

После запуска все контейнеры должны быть в состоянии `running`, а `db` и `gotenberg` — пройти healthcheck.

```bash
docker compose ps
docker compose exec db pg_isready -U docx -d docxdb
```

`app` не предоставляет отдельный health endpoint. Практическая проверка — открыть `/form`, заполнить тестовые данные с валидными датой приёма вызова и `kv_num`, нажать формирование и дождаться статусов. Затем убедитесь, что запись появилась в `/archive`, а файлы — в каталогах, выбранных для `DOCX_DIR` и `PDF_DIR`.

## Основной сценарий работы

1. Оператор открывает `/form`, заполняет данные и может продолжить черновик из браузера.
2. Отправка на `POST /generate` сохраняет запись и ставит рендер в очередь. Для этого требуются непустой `kv_num` и корректная дата приёма вызова.
3. Форма опрашивает статус записи до готовности или ошибки DOCX/PDF.
4. В `/archive` можно найти запись, открыть её карточку, посмотреть историю рендеров и скачать документы.
5. Сохранение через `POST /api/archive/save` допускает черновик без даты и без постановки рендера. При редактировании с тем же `kv_num` обновляется запись; изменение `kv_num` создаёт новую запись.

## API

| Метод и путь | Назначение |
| --- | --- |
| `POST /generate` | Валидация, сохранение и постановка версии в очередь |
| `GET /api/archive` | Список с фильтрами и пагинацией |
| `GET /api/archive/by-kv?kv_num=...` | Поиск точного `kv_num` |
| `GET /api/archive/:id` | Запись и история рендеров |
| `POST /api/archive/save` | Сохранить запись без рендера |
| `POST /api/archive/:id/render` | Поставить новую версию в очередь |
| `GET /api/archive/:id/download/docx?version=...` | Скачать выбранный DOCX |
| `GET /api/archive/:id/download/pdf` | Скачать актуальный PDF |

Сохраняются также совместимые маршруты `/archive/by-kv`, `/archive/save` и `/archive/:id/render`.

## Данные, миграции и документы

PostgreSQL хранит исходный payload (`raw_data`), данные для шаблона (`data`) и запись архива в таблице `archives`. Таблица `archive_renders` хранит версии, статусы, ключи файлов, ошибки и параметры повторных попыток PDF. Уникальный частичный индекс `archives_kv_num_uniq` не допускает повторов непустого `kv_num`.

Миграции применяются автоматически только при создании нового тома БД. Для существующей базы применяйте новые файлы вручную и по порядку, предварительно сделав резервную копию. Например, SQL-файлы доступны в контейнере `db` по `/docker-entrypoint-initdb.d/`:

```bash
docker compose exec -T db psql -U docx -d docxdb -f /docker-entrypoint-initdb.d/004_kv_num_unique.sql
```

Перед применением `004_kv_num_unique.sql` на старой базе устраните дубли непустого `kv_num`, иначе уникальный индекс не создастся.

DOCX-воркер подставляет данные в `template.docx` (плейсхолдеры `[[...]]`) и сохраняет DOCX по дате создания рендера и номеру версии. PDF-воркер читает готовый DOCX, отправляет его в Gotenberg и сохраняет PDF по дате приёма вызова и `kv_num`. Запись производится атомарно. Для временных ошибок PDF предусмотрено до трёх попыток; между первыми двумя повторными обработками используются задержки 5 и 30 секунд. Итоговая ошибка сохраняется в `archive_renders`.

Данные БД переживают пересоздание контейнеров благодаря именованному тому `db_data`. DOCX и PDF переживают его благодаря указанным bind mount'ам. Если каталог недоступен или недоступен для записи, соответствующий воркер отметит задачу как ошибочную (PDF может быть повторён); ссылка на файл вернёт 404, если файл отсутствует.

## HTTPS

nginx принимает HTTP на 80 и перенаправляет его на HTTPS 443. Сертификат и ключ монтируются из `nginx/certs/` только для чтения в `/etc/nginx/certs/`; ожидаются PEM-файлы `.crt` и `.key`, имена которых заданы в `nginx/default.conf`.

Если сертификат выдан локальным центром сертификации, доверенный корневой сертификат необходимо установить на клиентских устройствах. Проверить срок действия можно с хоста, указав фактическое имя сервера:

```bash
openssl s_client -connect <ИМЯ_СЕРВЕРА>:443 -servername <ИМЯ_СЕРВЕРА> </dev/null 2>/dev/null | openssl x509 -noout -dates
```

После замены файлов сертификата перезапустите nginx:

```bash
docker compose restart nginx
```

## Резервное копирование и восстановление

Резервная копия должна включать дамп PostgreSQL, каталоги DOCX/PDF, `template.docx`, `docker-compose.yaml`, `nginx/default.conf` и защищённую копию сертификатов. Скрипт резервного копирования создаёт дамп в `backups/` и удаляет дампы старше 14 дней:

```bash
./backup_db.sh
```

Скрипт использует зафиксированные в нём имя контейнера, БД и пользователя; перед применением в иной конфигурации проверьте и скорректируйте их. Храните копии вне сервера и проверяйте восстановление на отдельной среде.

`restore_db.sh` останавливает три прикладных контейнера и **удаляет существующую БД перед восстановлением**. Используйте его только после остановки записи новых данных и при наличии проверенной резервной копии:

```bash
./restore_db.sh <ПУТЬ_К_ФАЙЛУ_DUMP>
```

После восстановления верните документы, шаблон, конфигурацию и сертификаты из резервной копии, запустите сервисы и проверьте архив и создание нового документа.

## Журналы и диагностика

Все журналы выводятся в stdout контейнеров; файловых журналов проект не создаёт.

```bash
docker compose logs -f app
docker compose logs -f worker
docker compose logs -f pdf-worker
docker compose logs -f nginx
```

Проблема: DOCX имеет статус `failed`.

Возможная причина: нет `template.docx`, шаблон содержит ошибочные плейсхолдеры или недоступен каталог `DOCX_DIR`.

Что проверить: журнал `worker`, наличие шаблона в образе и права/монтирование каталога DOCX.

Проблема: PDF остаётся `pending` или становится `failed`.

Возможная причина: Gotenberg недоступен, истёк таймаут, превышен лимит размера PDF или отсутствует готовый DOCX.

Что проверить: `docker compose ps`, журнал `pdf-worker`, healthcheck Gotenberg и доступность общих каталогов DOCX/PDF.

Проблема: приложение не запускается.

Возможная причина: нет подключения к PostgreSQL; при первой ошибке соединения `app` завершает работу.

Что проверить: `docker compose logs app`, healthcheck `db` и согласованность `DATABASE_URL` с настройками PostgreSQL.

## Обновление и безопасность

Перед обновлением создайте резервную копию, получите изменения, сравните `docker-compose.yaml`, миграции и набор переменных, затем пересоберите сервисы. Новые миграции для существующей БД применяйте отдельно, после чего проверяйте журналы и полный путь «форма → DOCX → PDF».

```bash
git pull
docker compose up -d --build
docker compose logs --tail=100
```

В проекте не реализованы аутентификация и разграничение доступа. Поэтому ограничьте сетевой доступ к nginx и PostgreSQL средствами инфраструктуры, используйте HTTPS, не храните учётные данные и ключи в Git, ограничьте права на каталоги документов и резервные копии, а также регулярно обновляйте базовые образы и зависимости.

## Ограничения

- Генерация PDF зависит от доступности Gotenberg и общих каталогов файлов.
- Отдельного HTTP health endpoint у приложения нет.
- Миграции Docker автоматически выполняются лишь при инициализации пустого тома PostgreSQL.
- PDF скачивается только в актуальной версии, тогда как DOCX можно выбрать по версии.
- Наличие `kv_num` и корректной даты обязательно именно для формирования; черновик может быть сохранён без них.

## Лицензия

> Важно: SQL-скрипты из `./migrations`, проброшенные в `/docker-entrypoint-initdb.d`, выполняются только при первом старте нового volume `db_data`.
